# 設計理由

suimon の設計上の選択と、そのトレードオフを説明します。動作仕様と保証の正確な主張は [Lean の定義](../Suimon/)を参照してください。

## 制御と利用者の処理を分ける理由

ノード固有の処理内容までモデルに含めると、制御の証明が個々のアプリケーションや実装言語に依存します。そのため、実データを ID で抽象化し、期待する結果を [oracle](../Suimon/Oracle.lean) で表します。これにより、処理本体から独立して、実行順序・受け渡し・再試行の整合性を検証できます。実データの内容や外部副作用の正しさは、この抽象化の外にあります。

## 途中出力と全件待ちを組み合わせる理由

データを生成しながら下流で処理し、集約が必要な段階でだけ全件を待てるように、`emit` と `collect` を分けています。並列数の上限を `leaf` ごとに置くのは、アイテムごとの処理が複数段に分かれる場合にも、段階ごとの負荷を制限するためです。

## 配線で曖昧さを取り除く理由

`plain` と `stream` を接続時に区別し、暗黙の変換を設けないのは、上流の完了を待つ処理と、途中の到着から動く処理の取り違えをグラフの検証で見つけるためです。

`coalesce` で独立した処理から先に届いた値を採用すると、到着順で結果が変わってしまいます。単一の `branch` の排他的な経路に限定することで、値の選択をスケジューラから切り離します。内側のグラフの `branch` に再合流を求めるのも、選択経路によらず出口へ渡す値を一つに定めるためです。制約は [Graph.validate](../Suimon/Graph.lean) を参照してください。

## 到着順と再試行から結果を切り離す理由

並列実行で到着順まで固定すると、スケジューラに不要な制約が生じます。そのため、[決定性](../Suimon/Execution.lean)で比較する対象をアイテムの多重集合とし、`collect` の集約にも到着順を使いません。

ID を worker や試行に依存させないのは、再試行による再送を別の出力として数えないためです。一方、別の起動や別の入力経路まで重複排除しないよう、論理的な起動と経路は区別します。

## 停止と介入を明示する理由

利用者の処理が動き続けることなど、進行には制御モデルの外の前提も必要になります。そのため、安全性と進行性を分け、処理が進められない状態を明示します。

`blocked` からの解除を `manualRetry` にしたのは、単なる操作の再送によって、利用者の介入を待つ停止まで解除されることを避けるためです。

## 実行可能な定義を証明にも使う理由

実行用の遷移関数とは別に証明用の遷移関係を記述すると、二つの仕様を維持し、その一致も証明する必要が生じます。その重複を避けるため、実行と証明で [step](../Suimon/Step.lean) を共有します。

不変条件を検査して拒否できることだけでは、操作本体の正しさを示せません。そのため、[探索器](../Suimon/Explore.lean)では不変条件違反による拒否も反例として扱います。

## 履歴に内部状態をそのまま出さない理由

内部構造を直接 JSON にすると、証明や実装のためのフィールド追加が外部形式の変更になってしまいます。また、別言語の実装にも Lean の内部データ構造を要求してしまいます。これらを避けるため、[facts のフィールドを明示的に選び](../Suimon/Trace/Projection.lean)、状態の再構築に使う command と役割を分けます。

## 履歴の文字列化も証明に含める理由

操作列の再生が一致しても、文字列への符号化や読み戻しで値が変われば、復元経路の保証にはつながりません。そのため、符号化・復号を証明で扱える全関数として定義し、[記録から検査までをつないで証明します](../Suimon/Theorems/TraceWire.lean)。
