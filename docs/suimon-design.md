# 設計理由

動作と証明の対象は[自然言語仕様](suimon-spec.md)、正確な定義と証明済みの主張は [Lean の定義と証明](../Suimon/)を参照してください。

## 制御と利用者の処理を分ける理由

利用者の処理内容までモデルに含めると、制御の証明が個々のアプリケーションや実装言語に依存します。そのため、値は識別子だけで扱い、関数・判定・transform の結果は操作の引数として外から与えます。これにより、処理本体から独立して、受け渡し・分岐・停止・終了の整合性を検証できます。値の中身や外部への副作用の正しさは、この抽象化の外にあります。

## Single と Stream を宣言せず導出する理由

接続ごとに種別を書かせると、実際の動作と食い違う記述を許してしまいます。そのため、種別は関数の出力契約と制御の規則から[導出](../Suimon/Derive.lean)し、書かれた種別と動作を照合する必要そのものをなくしています。実行時の件数で種別を切り替えないのは、切り替えると検証時に導出した種別と実行時の形が食い違い、接続の検査を実行前に済ませられなくなるためです。

## 接続ごとに transform を必須にする理由

接続元の出力と接続先の入力を直接つなぐと、型の食い違いを検証で見つけられません。すべての接続に型付きの transform を置くことで、型の関係を接続ごとに閉じた形で検査できます。入力を取らない関数を何かの後に動かす場合も、値を捨てる `discard` を通すことで、上流が非選択なら非選択、失敗なら未実行という伝播を例外扱いせずに済みます。

## 識別子を来歴から決める理由

同じ値を二度 yield しても二つの結果として扱うため、結果は値ではなく来歴で識別します。来歴だけで決まる識別子は実行順によらず同じになるので、実行順によらない[結果の一致](suimon-spec.md#154-結果の一致)を識別子のまま比べられます。ランタイムが値に付ける識別子も、中身や到着順ではなく来歴から決めます。同じ振る舞いの実行が同じ記録を書き、要素の識別子から作る一覧の識別子も実行順に左右されないようにするためです。

[識別子](../Suimon/Identity.lean)は、各部分を長さ付きで連結し、先頭に種類のタグを置きます。JSON 文字列に埋め込む方式では、入れ子のたびにエスケープが倍に増え、Stream を重ねた経路で長さが指数的に伸びます。長さ付きの連結なら入れ子一段あたりの増加は定数で、逆変換があることを証明できます。タグを分けるのは、種類の違う識別子が偶然一致しないことを、単射性だけから示せるようにするためです。

## 実行を操作の列で表す理由

証明用の遷移関係を別に書くと、二つの仕様を保守し、その一致も証明する必要が生じます。そのため、エンジンの判断と外からの報告をすべて[操作](../Suimon/Step.lean)として一つの関数で扱い、探索・実行記録の生成と検査で同じ関数を使います。他言語の実装はこの関数を移したものだけで実行を進め、その記録をこの関数で再生して比べます。スケジューラの選び方は操作の順序として外に出し、証明はどの順序でも成り立つ形で述べます。

## 担当の喪失を失敗として扱う理由

利用者の関数を動かす側が止まったことは、タイムアウトを指定していない呼び出しでは検出できません。そのため担当期限を持たせ、期限切れはその呼び出しの失敗として停止／continue に従わせます。呼び直さないのは、止まったように見える担当者がすでに副作用を起こしたのか、まだ動いているのかをエンジンが知る方法がないためです。呼び直すと、二重実行や受理済みの要素の再送を扱う必要が生じます。

クラッシュ後の再開でも同じ理由で、実行中だった呼び出しは呼び直さず、担当の喪失として扱います。Go のランタイムは利用者の関数を同じプロセスで動かすため、クラッシュした時点で担当者も止まっており、再開時には期限を待たずに喪失を記録します。

## キャンセル後も終了を待つ理由

キャンセルを伝えた時点で終わったものとすると、枠がすぐ空いて次の並列対象が始まり、実際に同時に動く数が limit を超えます。そのため、キャンセルを伝えた呼び出しは実際に終了するまで枠を使い、実行範囲の完了や全体の終了もそれを待ちます。キャンセルに応じない処理があると終わらなくなりますが、それは仕様の[外部前提](suimon-spec.md#153-外部前提とエンジンの義務)として扱います。

ただし、担当が失われた呼び出しは応答する側がいないため、キャンセル中でもその時点で終了したものとし、枠を解放します。担当者が実際には動き続けていた場合、同時に動く数が一時的に limit を超え得ますが、応答しない担当者を待ち続けて実行全体が終わらなくなることを避けるため、こちらを選んでいます。

## 実行記録を自前の形式で書く理由

Lean 標準の JSON の出力と解析は検証されていないため、記録の文字列化と読み戻しで内容が変わらないことを証明できません。そのため、[記録用の値](../Suimon/Wire.lean)を固定のフィールド順で書き出す[符号化](../Suimon/WireText.lean)を自前で定義し、往復で元に戻ることを証明しています。書き出し方が一通りに決まるので、他言語の実装が書いた記録を Lean の出力とバイト単位で比べることもできます。

状態には値の識別子しか現れないため、再開後に後続へ値を渡すにはその中身（ペイロード）が要ります。ペイロードを別の保存先に置かず遷移の記録に含めるのは、値の保存と遷移の確定を一度の追記でそろえ、確定した遷移が失われた値を指す状態を復元時に扱わずに済ませるためです。

## 一覧を中身の集まりとして扱う理由

waitStream・Merge・concurrency の List の一覧は、仕様上、順序を保証しません。届いた順に並べると、一覧を受け取る処理の入力が実行ごとに変わり、結果の一致が崩れます。そのため、一覧の値は要素の集まりから決め、一覧を受け取る処理は並び順に依存しないことを利用者の前提とします。

## 結果の一致を実行どうしの包含で示す理由

スケジュールの違う二つの実行を、操作を入れ替えて同じ状態に寄せる証明（合流性）は、concurrency の枠の取り合いのように、一方を行うと他方が行えなくなる操作の組があるため、そのままでは成り立ちません。そのため、完了した実行の状態が、同じ環境に従う別の実行の記録をすべて含むことを一手ずつ示し、両方向の包含から[一致](../Suimon/Theorems/Round3/Determinism.lean)を導いています。操作の組ごとの入れ替えを証明せずに済み、補題が操作の種類ごとに分かれるので、並行して証明を進められます。

## 他言語の実装を記録で確かめる理由

各言語の実装とモデルの同値性を形式的に証明するのは、実装言語ごとに大きな作業になります。代わりに、実装が書いた実行記録を Lean の検査器で再生し、状態まで一致することを確かめます。記録が同じ状態遷移で説明できることは確かめられますが、実装全体の正しさの証明ではありません。
