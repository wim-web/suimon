# 設計理由

suimon の動作仕様は Lean の定義に置く。この文書では、定義を選んだ理由とトレードオフを説明する。保証の前提と限界は [保証の読み方](implementation.md)、検査器の使い方は [イベント履歴の利用](trace-format.md) を参照。

## 制御と利用者の処理を分ける理由

証明したいのは、処理の順序、アイテムの受け渡し、再試行、完了の整合性である。ノードが行う取得・評価・執筆などの処理までモデルに含めると、制御の証明がアプリケーションや実装言語に依存する。

そこで、実データは象徴的なアイテム ID で扱い、利用者の処理結果は [Oracle.lean](../Suimon/Oracle.lean) の oracle として受け取る。外部実装は、自身の実行履歴をモデルの論理 ID と操作へ対応付けて検査できる。データの内容や外部副作用の正しさは、この抽象化の外にある。

## yield と AllWait を組み合わせる理由

記事を探す Scan が数分かけてアイテムを出し続ける場合、Scan 全体の終了を待ってから取得を始めると、途中で得た記事を処理できない。一方、記事の集合を使って計画を作る段階では、Scan の終了と全記事の処理完了の両方を待つ必要がある。

yield は前者の待ち時間を取り除き、AllWait は後者の完了境界を表す。処理段階ごとに同時実行数を制限できるよう、ForEach 全体の直列化ではなく leaf ごとの上限を選んだ。AllWait に相当する定義名は `collect`。実行可能な例は [streaming.json](../Test/graphs/streaming.json) にある。

## 配線で曖昧さを取り除く理由

plain と stream は共通のトークン列で表現できるが、接続時には区別する。これにより、「上流の完了した値を受ける」と「到着したアイテムから処理する」の取り違えをグラフの検証で見つけられる。暗黙の変換を設けず、stream をまとめる箇所には Collect を明示する。

並列経路の合流と Branch の排他的合流も分ける。Coalesce を独立した処理の first-wins にすると、到着順で結果が変わってしまう。単一 Branch の arm に由来する入力に限定することで、値の選択をスケジューラから切り離す。body 内の Branch に再合流を求めるのは、選択経路にかかわらず body の出口へ渡す値を一つに定めるためである。

配線の制約は [Graph.lean](../Suimon/Graph.lean) の `Graph.validate` に置く。[coalesce-loop.json](../Test/graphs/coalesce-loop.json) は Loop 内の再合流、[coalesce-stages.json](../Test/graphs/coalesce-stages.json) は複数段の再合流の例である。

## 到着順と再試行から結果を切り離す理由

並列実行で再現したいのは、各線を通るアイテムとその個数である。到着順まで固定すると、スケジューラに不要な制約が生じる。Collect の集約順に安定した ItemId の順序を使うのも、到着順を結果へ持ち込まないためである。

再試行による再送と、別の起動による同じ値の生成は区別する必要がある。アイテム ID は論理的な出力 occurrence を識別し、worker や attempt に依存させない。Loop や Sub の起動は path で分ける。Merge では入力線の違いを残し、fan-out 後に戻った別々の occurrence を誤って重複排除しないようにする。

モデルでは ID の構成要素を JSON 配列で符号化する。実装で digest を使うなら、モデルへの対応で衝突しないことが必要になる。識別子とスコープの定義は [State.lean](../Suimon/State.lean)、決定性の前提は [Execution.lean](../Suimon/Execution.lean) を参照。

## 停止と介入を明示する理由

処理が必ず進むという主張には、worker が動き続けることなど、制御モデルだけでは与えられない前提が要る。suimon では安全性の証明を中心に置き、実行可能な作業が見つからない状態を明示する。`hasWork` の判定範囲と進行性の保証は分けて読む必要がある。

blocked からの解除を明示的な `manualRetry` にしたのは、操作への単なる再送で介入待ちが解除されることを避けるためである。Loop の上限追加は個々の起動に限定し、完了した反復をやり直さず、他の起動の上限も変えない。制御上の判断は [Step.lean](../Suimon/Step.lean) にある。

## 実行可能な定義を証明にも使う理由

遷移関数 `step` を実行と証明で共有する。独立した遷移関係をもう一つ記述すると、同じ仕様を維持し、その一致も証明する必要が生じる。`Graph.WellFormed` も実行可能な検証の成功として定義し、証明に必要な構造的性質をそこから取り出す。

不変条件の検査も受理条件に含める。このため、「受理された操作の安全性」と「操作本体が不変条件違反を起こさないこと」は異なる主張になる。探索器が不変条件違反による拒否も反例として報告するのは、検査で拒否できたことを実装の正しさと取り違えないためである。

Lean の標準ライブラリで扱える範囲では外部パッケージを追加せず、ビルドと検証に必要な依存を抑える。

## 履歴に内部状態をそのまま出さない理由

内部構造を直接 JSON にすると、証明や実装のためのフィールド追加が外部形式の変更になってしまう。facts は [Trace/Projection.lean](../Suimon/Trace/Projection.lean) で公開フィールドを選び、論理 ID に基づく順序で記録する。

command は状態の再構築に、facts は外部実装が記録した効果との照合に使う。これにより、外部実装に Lean の内部データ構造を要求せず、操作の受理と効果を検査できる。形式の変更と移行については [イベント履歴の利用](trace-format.md) を参照。

## 履歴の文字列化も証明に含める理由

操作列の replay が一致しても、文字列への符号化や読み戻しで値が変われば再開の保証にはつながらない。Lean 標準 JSON printer / parser の内部には、カーネルから展開して一般証明に使えない部分関数がある。そのため、suimon が出力する v2 の表記には全関数の codec を用意し、文字の escape、数値、入れ子、全 Op の往復を組み立てて証明する。

入力の互換性は維持し、別の空白やキー順は標準 parser から同じ検査器へ渡す。facts は JSON の構造をトークン列として比較するので、復号時に内部の map の形を再現する必要はない。公開フィールドと意味は v2 のままである。証明の範囲は [保証の読み方](implementation.md#replay-と外部環境) を参照。
