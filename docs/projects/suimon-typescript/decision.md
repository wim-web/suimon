# TypeScript 実行器の設計理由

Go と同じ操作を受け付ける純粋な状態遷移を一つ置き、実行と journal 再生の双方で使う。各制御が直接次の処理を await する別インタープリターは、復元用の遷移と二重実装になるため採用しない。状態を変更する主体は実行ごとに一つとし、callback は完了イベントだけを返す。

状態遷移を一つずつ準備し、journal の append と sync が成功してから関数起動・生成器取得・abort・完了報告を公開する。最初から複数遷移の保存をまとめず、障害時に公開してよい範囲を小さく保つ。性能改善はこの境界を変えずに行える。

型付き構築は値・transform・接続先の対応を保持する。DAG、入口、終点、Single／Stream の導出は既存検証器に任せる。保存から戻る値は unknown なので、型名だけで型を保証せず、利用者が指定する parser を通す。

構成の uint64 は bigint として保持する。一般の JSON.parse と JSON.stringify だけでは、整数の精度、重複キー、文字列のエスケープ、識別子の Unicode 文字数を Go／Lean と一致させられない。定義と trace の codec を明示的に実装し、payload 文字列を checker が JSON と決めつけない。

アーキテクチャ比較では四案とも共通の状態遷移を選んだ。D 案の start／run／resume と Promise の完了契約を基に、A 案の必須 parser と制御別の型を取り入れる。独立レビューも同じ選択を推奨した。完了値を二重の union で包む案と、初期段階の独自ファイルロック実装は採用しない。永続化はバイト列の adapter 契約で閉じ、Neo が Postgres の所有権を管理する。
