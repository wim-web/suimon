## 1. 目的と責務分担

利用者が定義した処理を接続し、結果の受け渡し、分配、分岐、並行実行、Stream、集約を制御するworkflowエンジンを提供する。

**エンジンは制御を提供し、利用者は処理本体・入出力型・接続ごとのtransformを定義する。** 単純なin/outノードも、利用者処理を呼ぶために提供する枠組みに含む。

| 提供側の責務 | 利用側の責務 |
| --- | --- |
| in/out、branch、concurrency、サブworkflow、waitStream、Merge、複数の接続への分配の制御 | 各ノードの処理本体と入出力型 |
| 型付きのノード・接続契約と受け渡し | 接続ごとのtransform |
| 判定結果に従う分岐 | branchの判定処理 |
| 起動、結果の受理、終了、非選択、失敗、タイムアウト、担当の喪失、キャンセル、実行記録と復元の管理 | ノードの配置・接続・実行設定 |
| 検証あり／なしの実行API | 使用する実行APIの選択 |

仕様と証明の基準はLeanに置く。Goなど特定の実装言語を、制御仕様の前提としない。

### 1.1 制御の役割

| 仕組み | 役割 |
| --- | --- |
| 複数の接続 | 同じ結果を、複数の行き先へ配る |
| branch | 値や要素ごとに、行き先を一つ選ぶ |
| Stream | 件数が実行時に決まる要素を、届いた順に流す |
| concurrency | 入力一件ごとに、登録した並列対象を並行実行し、結果を一つの出力にまとめる。limitで同時に動かす数を抑える |
| サブworkflow | 別に定義したworkflowを、一つのノードとして呼ぶ。入力一件ごとに、その中の流れをエンジンが管理する |
| waitStream／Merge | Streamを一覧にする／Single同士を一覧にまとめる |

## 2. 用語、ノード定義、配置

| 用語 | 意味 |
| --- | --- |
| workflow実行 | 一つのworkflow定義を実行する一回分 |
| ノード定義 | 制御の種類、処理本体、入出力の型契約。処理本体は関数、またはサブworkflowとして使うworkflow定義 |
| ノード配置 | ノード定義をグラフの特定の位置で使うこと。配置ごとの名前・接続・設定を持つ |
| ノード呼び出し | 入力一件などを契機として、配置されたノードの処理を一回適用すること。Stream出力では、その生成の終了までを含む |
| Stream生成器 | yieldで値を順次生成する利用者処理の実行状態。独立したノード種別ではなく、同期・非同期のジェネレータなどで実現する |
| サブworkflow | 別に定義したworkflowを、ノードの処理本体として呼ぶもの。呼び出しごとに一つの実行範囲になる |
| 並列対象 | concurrencyのtasksに登録する一項目。関数、またはサブworkflow |
| concurrencyの一回の実行 | そのconcurrencyを一回適用し、登録した並列対象一式を動かすこと |
| 実行範囲 | workflow実行、サブworkflowの一回の呼び出し、concurrencyの一回の実行などに属する処理・結果・状態をまとめて識別する範囲 |
| 辺・接続 | ノード間で結果を渡すための定義 |
| EOS | 対象のStreamに、それ以上の結果が追加されないことを知らせる終了通知 |
| 呼び出しの担当・担当期限（lease） | 利用者の関数の一回の呼び出しを実行する実行基盤側の主体（エンジン自身、または別プロセスのworker）と、その主体が実行を続けていることを示す期限 |
| 実行記録 | 受理した状態遷移を順に追記した記録。一つの状態遷移に伴う記録は、確定の印までを一組とする |

ノードは接続先と独立に定義できる。同じノード定義を一つのグラフに複数配置できる。異なる配置は別の接続・状態を持ち、終点の結果名にも配置の名前を使う。

ノード定義と、実行時の状態を分離する。同じ配置を複数の入力について呼び出す場合、それぞれの完了・失敗・非選択を混ぜない。

実行範囲の識別はエンジン内部の責務とする。利用者に結果照合用のキーを書かせることは前提としない。

## 3. workflowの入力と接続

### 3.1 workflowの外部input

**runおよびrunUncheckedの呼び出し側はworkflowの外部にある。** 呼び出し側は、そのworkflowで宣言されたInput型の値を一つ渡す。inputを必要としないworkflowも認める。

呼び出し側へ、workflow内部の辺、Single／Streamの種別指定、EOSなどの制御情報を組み立てさせない。両実行APIで、外部inputの契約は共通とする。

```
run(workflow, input)       // 宣言されたInput型の値を一つ渡す
run(workflow)              // inputを必要としないworkflow
```

inputを受け付けるworkflowは、その型と、最初にinputを渡す入口を定義に持つ。エンジンは一回のworkflow実行の開始時に、その値を入口の入力として一回供給する。これは呼び出し側にSingleの辺を作らせる契約ではない。workflow内部の種別の導出では、入口への入力を、そのworkflow実行範囲に対するSingleとして扱う。

**Single／Streamは、workflow内部の結果と接続の契約である。** 最初の処理が通常の値をreturnするか、yieldで値を生成するかは、そのノードの出力契約によって定める。外部inputの件数・実行回数と、内部で生成するStreamの要素数を混同しない。

例えば、外部から配列をinputとして渡しても、それは宣言された入力値一つである。その各要素を内部Streamへ流す場合は、利用者のノードがその配列からyieldする。外部の反復可能な値を受け取る場合も、通常のInput型の値としてノードへ渡し、workflow内での生成はノードの契約に従う。呼び出し側が内部のStream制御を担当するものではない。受け渡す値の性質についての利用者の保証は、第4.4節に従う。

複数の入口名に別々のinputを渡す実行APIは、初版には設けない。

入力なしで開始するノードは、所属する実行範囲を開始したときに一回、起動対象になる。サブworkflowの中に配置した入力なしノードは、そのサブworkflowの呼び出しごとに扱う。入力なしであることを理由に、外側の分岐やキャンセルを無視して起動しない。

### 3.2 入力接続の本数

**通常ノードの入力接続は1本までとする。** 入力を必要としないノードは0本でよい。

入力を必要としないノードにも、値を渡さないtransform（discard、第4.2節）で1本つないでよい。その場合は、届いた値を渡さず、届いたことを契機に呼び出す。Streamを受ければ要素ごとに呼ぶ。上流が非選択なら非選択、上流が失敗なら上流失敗による未実行とする。

複数の結果を合流させる場合はMergeを使う。通常ノードに複数の接続を直接入れ、暗黙に待ち合わせることはしない。

構造体の複数フィールドは、一つの入力値の中身である。フィールドごとに入力接続を作る必要はない。

### 3.3 接続の指定

接続は、接続元、接続先、transformを指定して構築する。branchの選択先など、複数経路を区別する情報も接続契約に含める。一つの出力から複数の接続を出してよい（第6節）。

利用者にデータのフィールドごとの接続口を定義させない。内部の接続識別情報と、利用者が扱うデータ型は別にする。

## 4. 利用者処理とtransform

### 4.1 Singleはreturn、Streamの要素はyieldで出す

**通常の利用者処理は、宣言した出力契約に従い、Singleではreturnで一つの値を返し、Streamではyieldで各要素を生成する。** 出力契約はノード定義に持たせる。実際に得られた要素数を見て、SingleとStreamを切り替えてはならない。

| 一回の呼び出しの出力契約 | 利用者が定義する処理 | エンジンが受け取る結果 |
| --- | --- | --- |
| `Single<T>` | 一つの値Tをreturnする。非同期処理なら、その完了時に値を返す | 正常終了時に一つのT、または失敗 |
| `Stream<T>` | 同期・非同期のジェネレータなどでTをyieldする | yieldされた0件以上のTと、生成の正常終了または失敗 |

**Streamを返すことと、全件を作り終えてから一覧を返すことは異なる。** Streamでは、新しい要素が生成されるたびに、エンジンがその要素を受理・保存・公開し、後続へ渡せる。生成する件数が、実行時の入力やAPIの応答によって決まってよい。

例えば、以下は異なる契約である。記法は疑似コードであり、特定の実装言語を要求しない。

```
出力契約：Single<List<T>>
    return [a, b, c]
    → 一覧全体を一つの結果として渡す

出力契約：Stream<T>
    for value in 取得した一覧:
        yield value
    → a、b、cを別々の結果として渡す
```

一覧の要素を順次yieldする処理は、利用者定義のStream出力ノードとして記述できる。そのためだけの専用expandノードは、初版の必須制御に含めない。通常の値としてreturnされた一覧や構造体を、エンジンが勝手に展開してはならない。

非同期のStream生成器では、外部処理の応答を待ち、その時点で得られた値をyieldしてよい。全件の取得完了を待つことを要求しない。利用者の処理内部で非同期処理を並行させてもよいが、エンジンから同じ生成器を読み進める操作は第4.1.1節に従って順次行う。

**利用者向けの直接的なemit APIは設けない。** 利用者は各言語のジェネレータなどでStreamを返し、エンジンはそのStreamから要素と終了を取得する。emitを持たないことを、一回の処理から複数要素を生成できないという制限にしてはならない。

#### 4.1.1 Stream生成の実行契約

Stream生成器を返しただけでは、そのノード呼び出しは完了しない。生成器が正常に終了するか、生成が失敗するか、キャンセルにより終了するまで、対応する呼び出しを未完了として管理する。

**エンジンは、前の取得が完了する前に、同じ生成器へ次の取得を要求してはならない。** 一つの生成器について、要素の取得と終了確認を順次進める。異なる呼び出しの生成器や、concurrencyの異なる並列対象の生成器は、相互の全件終了を待たずに進めてよい。

利用者処理は、呼び出しごとに独立した生成状態を提供する。同じ進行中の反復子の読み取り位置を、異なる呼び出しに共有してはならない。設定値や外部資源の共有まで一律に禁止する意味ではない。

**後続の処理完了や未処理件数を、生成器の次の取得要求の条件にしない。** 前の取得と、その結果の受理・保存を進めた後、後続の全件完了を待たずに次の取得を進める。取得・保存自体に必要な時間や公平なスケジューリングは認めるが、遅い後続のための意図的な読み進め停止は行わない。停止・キャンセル時は第11節に従い、新しい取得を行わない。この読み進め方は、実行基盤の要件としても扱う。

生成器が正常終了するまでに一度も要素を生成しなかった場合は、正常な空のStreamとする。生成器を作る処理自体が非選択だった場合のskippedとは区別する。

生成器の準備中・読み進め中に失敗した場合は、その生成処理を持つノードの停止／continue設定に従う。continueでは、その生成器を失敗として終了させ、残りの独立した呼び出し・経路を進める。同じ生成器を自動で再開・再試行しない。

失敗前に受理した要素は、成功結果として保持する。後から生成が失敗したことを理由に撤回しない。停止・キャンセル後の要素は、第10節・第11節に従い受理しない。

**Streamの結果データはyieldされた要素だけとする。** Stream処理の終了は、追加の結果を伴わない終了として扱う。言語の生成器終了に戻り値が付随しても、それを追加のTや別の最終結果として受理・公開しない。通常のSingle処理がreturnで結果を返す契約とは区別する。

複数生成器の結果をまとめる場合のEOSは、個々の生成器が一つ終了しただけでは確定せず、第10.3節に従う。

利用者処理内部のスレッドなどを、エンジンがworkflowの並列対象として発見・管理することはしない。利用者処理およびStream生成器は、出力とキャンセルの契約を守る。

### 4.2 接続ごとのtransform

各接続にはtransformを指定する。接続元の出力型がA、接続先が受け取る型がBなら、そのtransformの型契約はA→Bとする。

transformは副作用のない変換層であり、その接続元の結果だけを受け取る。エンジンは変換内容を知らなくてよいが、型付き構築APIは接続元・transform・接続先の型関係を保持しなければならない。

transformは省略しない。型が同じ場合に指定できるパススルーtransformを、ライブラリから提供してよい。

入力を必要としない接続先には、ライブラリが提供する、値を渡さないtransform（discard）を指定する。discardは任意の型の値を受け取り、失敗しない。

Stream接続では、各要素にtransformを適用する。一覧全体を変換する場合は、先にwaitStreamでSingleにする。

transformは失敗し得る。失敗には接続先ノードの停止／continue設定を適用する。continueでは、その値による接続先処理の呼び出しを行わず、残りを処理する。

### 4.3 Mergeにも接続ごとに変換する

```
Aのoutput → transformA → T ─┐
                            ├→ Merge
Bのoutput → transformB → T ─┘
```

transformAにBの結果まで渡すことはしない。Merge共通の利用者処理やtransformを別に設けない。

### 4.4 受け渡す値についての利用者の保証

**入力・結果として渡す値が、接続先での利用方法と、実行基盤の保存・受け渡しの方式に適していることは、利用者が保証する。** 保存・受け渡しの方式に求める条件（直列化できることなど）は、実行基盤が示す。

エンジンは、値に含まれる反復子やチャネルを複製したり、消費済みの内容を復元したりしない。接続先で値を変更した場合に、その変更がほかの接続先や保存済みの結果へ反映されるかどうかは保証しない。

エンジンが保証するのは、受理した各結果を対象の各接続へ欠落・余計な重複なく渡すことであり、値の内部の状態や使われ方ではない。エンジンがStreamとして受理した各要素を複数の接続へ配ることは、エンジンの責任とする。

### 4.5 サブworkflow

**ノードの処理本体として、関数の代わりに、別に定義したworkflowを指定できる。これをサブworkflowと呼ぶ。** サブworkflowは、呼び出し元のworkflow実行の一部として動く。

| 項目 | 規則 |
| --- | --- |
| 入力 | サブworkflowのInput型の値を一つ受け取る。呼び出し元の入力接続のtransformで、その型にする。Input型を持たないサブworkflowは、入力なしのノードとして配置する |
| 出力 | 終点を一つ指定し、その結果を一回の呼び出しの出力（Single）とする。出力は、その呼び出しが完了してから後続へ渡す。ほかの終点の結果は呼び出し元へ返さない |
| 実行範囲 | 呼び出しごとに一つの実行範囲になる。Streamを受ければ要素ごとに呼ばれ、各呼び出しの中では要素をSingleとして扱う |
| 状態 | 出力に指定した終点の状態を、呼び出しの状態として後続へ伝える。非選択なら非選択、上流失敗なら上流失敗による未実行とする |
| 失敗・停止 | 中のノードの失敗は、中のノードの停止／continue設定に従い、呼び出し元のworkflow実行の失敗として記録する。中での停止は、workflow全体の停止とする。呼び出し元の停止・キャンセルは、中の処理にも伝える |
| 完了 | 出力に指定しない終点を含め、中の処理がすべて終了した時点で、その呼び出しを完了とする |

サブworkflowの中の失敗を理由に、呼び出し元の配置で停止方針を再適用しない。呼び出し元の配置の停止／continueは、その入力transformの失敗に適用する。

サブworkflowの中のノードへ、呼び出し元から直接接続してはならない。外との受け渡しは、入力と、出力に指定した終点だけで行う。workflowが自身を直接または間接に呼ぶ構成は認めない。

## 5. Single／Streamの意味と導出

### 5.1 基本契約

| 種別 | 意味 |
| --- | --- |
| Single | 対象の実行範囲で、成功結果を一つ渡す接続 |
| Stream | 成功結果を0件以上順次渡し、終了時にEOSを知らせる接続 |

Singleでも、失敗・非選択・キャンセルの場合には正常な結果がない。値と、値が得られない理由は分離して管理する。

`Single<List<T>>`は一覧を一つ渡す接続、`Stream<T>`は各要素を順次渡す接続である。両者を暗黙に同一視しない。

Single／Streamは実行範囲に対する性質である。Streamの各要素に対してサブworkflowやconcurrencyを適用する場合、その一回の呼び出し・実行の中では、要素をSingleとして扱う。複数の呼び出し・実行の結果を外側へ送る接続はStreamになる。

### 5.2 種別は制御規則から導出する

通常ノードでは、入力の種別と、一回の呼び出しに対する出力契約を区別する。

| 通常ノードへの入力 | 一回の呼び出しの出力契約 | 接続全体の出力 |
| --- | --- | --- |
| なし／Single | `Single<T>` | `Single<T>` |
| なし／Single | `Stream<T>` | `Stream<T>` |
| Stream | `Single<T>` | 各呼び出しが返したTを流す`Stream<T>` |
| Stream | `Stream<T>` | 各呼び出しが生成したTを一本に流す`Stream<T>` |

Stream入力・Stream出力の場合、転送上の`Stream<Stream<T>>`を新設しない。各入力に対する生成器の要素を、一つの出力Streamへ流す。一つの生成器が終わるまで他の生成器の要素を待たせることや、入力ごとに連続した並びで出力することは保証しない。

入力ごとの一覧を必要とする場合は、その入力に対してサブworkflowを呼び、その中にwaitStreamを置く。外側に置いたwaitStreamは、外側の一本のStreamに流れた成功要素全体を集約する。

| その他の制御 | 出力の種別 |
| --- | --- |
| branch | 各経路とも入力と同じ種別 |
| waitStream | `Single<List<T>>` |
| Merge | `Single<List<T>>` |
| サブworkflow | 一回の呼び出しの出力はSingle。接続全体の種別は、Single出力の通常ノードと同じ規則で導出する |
| concurrency | 第8.3節の出力の形と、外側の入力種別から導出する |

一つの出力から出る複数の接続は、どれも同じ種別になる（第6節）。

接続種別を保存形式に記載する場合は、導出結果と一致しなければならない。記載によって本来の動作を変更してはならない。

Streamの生成経路には、利用者処理が返すStream生成器、concurrencyのStream出力、既存のStreamを受けた各呼び出しの結果を一本に流す動作がある。結果件数を、定義時に固定された並列対象の数だけに限定しない。

### 5.3 通常ノードへのStream入力

各要素に接続のtransformを適用し、その結果を使って通常ノードを一回ずつ呼ぶ。

出力契約がSingleなら、成功した戻り値を出力Streamへ渡す。出力契約がStreamなら、その呼び出しの生成器から受理した各要素を出力Streamへ渡す。いずれも、失敗した値の代わりの要素は作らない。

**通常ノードに独自のlimit・同時起動数設定は設けない。** concurrencyのlimitは第8.2節の登録済み並列対象を制限するものであり、Stream全体の入力件数に対する共通上限ではない。

**Streamの同時処理入力件数や、Stream入力のconcurrencyの同時適用数を制限する設定は、初版には設けない。** この範囲の並列度について、利用者が指定した一定件数以下に収める保証を追加しない。これは無制限の計算資源を保証する意味でも、全件を必ず同時に開始するという指定でもない。

値の順序と処理完了順は保証しない。エンジンは、第15節の進行・終了の義務を満たしながら処理を進める。

一覧を受け取って一回だけ処理したい場合は、Stream→waitStream→通常ノードと接続する。

### 5.4 順序と同じ値

Stream、waitStream、Mergeの一覧について、順序は保証しない。

値が等しくても、別々の呼び出しから得た結果は別の結果として扱う。同じ生成器が同じ値を二度yieldした場合も、二つの要素として扱う。値が等しいことだけを理由に、エンジンが重複排除してはならない。

## 6. 複数の接続による分配

**一つの出力から、複数の接続を出してよい。** 通常ノード、branchの各経路、サブworkflow、concurrency、waitStream、Mergeのいずれの出力でもよい。分配のための専用ノードは設けない。

同じ結果を、各接続へ渡す。各接続は同じ種別になり、Singleなら各接続もSingle、Streamなら各接続もStreamとする。Streamの場合は、各要素とEOSを各接続へ伝える。一本のStreamの中に同じ要素を何件も挿入するものではない。

各接続のtransformは個別に適用する。一つの接続のtransformの失敗は、その接続先の失敗方針に従う。

**複数の接続の先は、それぞれ独立した処理経路とする。** 各接続先は互いを待たずに進み、どちらが先という順序もない。実際に同時に動く件数は、実行基盤の資源による（第5.3節）。各経路の結果を入力ごとに自動照合せず、一覧の同じ位置を対応する結果とみなさない。

同じ入力について複数処理の結果を一組にする場合は、その入力に対するconcurrencyやサブworkflowの中で処理・合流する。

分配した後のMergeは任意である。各経路が別の終点へ到達してよい。

## 7. branchと非選択

### 7.1 判定と経路

branchはN択を認める。一回の成功した判定で一つの経路を選択する。判定結果は、そのbranchに定義された経路を識別する値とする。

Stream入力では各要素について判定する。判定処理は利用者が定義し、通常の利用者処理と同様に外部アクセスなどを行ってよい。

判定処理の失敗にはbranch自身の停止／continue設定を適用する。入力transformの失敗にも、接続先であるbranchの設定を適用する。判定できなかったことを、正常な非選択に置き換えない。

「何もせず終わる経路」を明示的に定義してよい。その経路が選ばれた場合、値を後続へ渡さず処理を終える。定義した無処理経路と、存在しない接続先への誤った接続は区別する。すべての経路を無処理経路にすることは認めない。少なくとも一つの経路は接続先を持つ。

### 7.2 非選択の扱い

選択された経路へ値を渡す。非選択側の通常処理と、その出力先へ向かうtransformは呼ばない。

非選択はエンジン内部の状態として扱い、利用者データにSkippedなどを混ぜない。

一要素でその経路を選択しなかったことを理由に、経路全体のStreamを途中で閉じてはならない。後続要素で選ばれる可能性がある。

### 7.3 EOS時の判定

入力StreamのEOSと、そのbranchで進行中の判定が終わることを確認し、経路の終了状態を決める。

**実際にbranchへ届いた入力に対する判定を使う。上流で失敗して届かなかった要素を、仮想的な判定対象に加えない。** 上流の失敗記録とworkflow全体の失敗は、そのまま保持する。

| 状況 | その経路と後続waitStreamの扱い |
| --- | --- |
| 正常な判定が1件以上あり、すべて別の経路を選び、このbranch自身の判定・入力変換には失敗がない | 経路全体をskippedにする。waitStreamも値を出さない |
| 上記に該当し、branchへ届く前の処理にはcontinueの失敗がある | 同じくskipped。上流失敗を理由にその枝から空の一覧を出さない |
| 経路は選ばれたが、その後の処理が正常に結果0件で終了した | 正常な空のStreamとして扱い、waitStreamは空の一覧を返す |
| 経路は選ばれたが、continueで成功分が0件となった | waitStreamは空の一覧を返す。失敗記録は維持する |
| branchへ届いた入力が0件で、経路全体のskipped通知を受けたわけではない | 空のStreamとして閉じる。上流に失敗があれば、その記録は維持する |
| このbranch自身の判定・入力変換がcontinueで失敗し、選択結果が得られなかった | その失敗をskippedとみなさない。得られた成功分を扱い、成功分0件なら空の集約結果と失敗記録を残す |
| branchを含む経路全体が外側の分岐で非選択となった | その非選択を後続へ引き継ぐ |

出力件数が0件という観測だけで、skippedを決めてはならない。

この区別は、通常ノード、複数の接続、サブworkflow、concurrencyの出力、waitStreamを通過しても維持する。複数の供給元からStreamを作る場合、候補が存在し、そのすべてが正常な非選択だったときはskippedとする。候補自体が0件の場合や、正常な空結果、失敗が原因の0件とは区別する。

## 8. concurrency

### 8.1 登録する並列対象

**concurrencyは、入力一件ごとに、登録した並列対象を並行実行し、その結果を一つの出力にまとめる。** 並列対象は、関数またはサブworkflowである。concurrencyの内部にノードを配置することはしない。複数のノードからなる処理を一つの並列対象にする場合は、サブworkflowとして定義する（第4.5節）。

```
concurrency(
    limit  = 2,
    tasks  = [fetchProfile, profileFlow, fetchOrders],   // 関数、またはサブworkflow
    output = List,                                       // List または Stream
)
```

concurrencyへ入る接続は0本または1本とする。一回の実行では、すべての並列対象が同じ入力から始まる。複数のSingle結果をまとめる必要があれば、concurrencyへ渡す前にMergeで一つの入力にする。StreamをMergeへ直接入れる例外は設けない。

各並列対象には、次を指定する。

| 項目 | 内容 |
| --- | --- |
| 処理本体 | 関数、またはサブworkflow。関数の契約は第4.1節の通常の利用者処理と同じで、Singleをreturnするか、Streamの要素をyieldする |
| 入力transform | concurrencyへの入力を、並列対象の入力型へ変換する。入力を必要としない並列対象ではdiscardを指定する。concurrencyに入力がなければ指定しない |
| 出力に含めるか | 含めない並列対象の結果は捨て、出力の要素型Tにそろえる必要もない。完了と失敗は、concurrency全体の判定に含める |
| 出力transform | 並列対象の結果を、出力の要素型Tへ変換する。出力に含める並列対象だけに指定する |
| 停止／continue | その並列対象の関数の失敗と、その入力・出力transformの失敗に適用する。サブworkflowの中の失敗には、中のノードの設定を適用する |

transformは省略しない。型が同じ場合は、パススルーtransformを使ってよい。

出力に含める並列対象は、1つ以上とする。

並列対象同士を接続することはない。並列対象は、互いの結果を待たずに進む。

### 8.2 limit

**limitは、一回のconcurrency実行の中で、同時に進める並列対象の数を制限する。** 正の整数を明示指定する。省略は認めない。

並列対象は、入力transformが成功したあと、枠を取得して開始し、その並列対象が終了するまで1枠を使用する。空き枠がなければ、枠が空くまで開始を待つ。入力transformは枠を使わず、枠の空きを待たずに行う。Streamをyieldする関数では生成器の終了まで、サブworkflowではその呼び出しの完了までを含む。タイムアウトや停止でキャンセルを伝えた並列対象は、実際に終了するまで枠を使い続ける。入力transformの失敗で起動しない並列対象は、枠を消費しない。

サブworkflowの中にあるconcurrencyは、自身のlimitで自身の並列対象を管理する。呼び出し元のconcurrencyの枠と、同じプールとして扱わない。

同じconcurrencyを異なる入力に適用したとき、limitは各適用の登録対象に対する上限である。workflow全体やStream全体を横断する共通上限とは解釈しない。Streamの同時処理入力件数やconcurrencyの同時適用数を制限する別設定は、初版では提供しない。

### 8.3 出力

concurrencyの出力は、次のどちらかを定義で指定する。

| 出力 | 一回の実行の出力 | 動作 |
| --- | --- | --- |
| List | `Single<List<T>>` | 出力に含める並列対象の成功結果を、すべての並列対象が終了してから一覧で返す。Streamをyieldする並列対象は、その各要素を一覧に含める |
| Stream | `Stream<T>` | 出力に含める並列対象の成功結果を、得られた都度に一本のStreamへ流す。Streamをyieldする並列対象は、その各要素を流す |

出力の種別は定義で決まり、実行時の件数で変えない。Stream出力で成功結果が一件でも0件でも、Streamのままとする。エンジンが自動でanyやタグ付きの別型へまとめ直すことはしない。

一覧とStreamの順序は保証しない。並列対象を区別する必要があれば、出力transformの結果にその情報を含める。

Stream出力の各結果は、concurrency全体の終了前から渡せる。EOSは、出力に含めない並列対象を含め、すべての並列対象が終了してから確定する。

結果が得られなかった並列対象は、次のように扱う。

- 失敗した並列対象の値は作らず、成功分だけを出力する。失敗記録は消さない。
- Streamをyieldする並列対象が途中で失敗しても、それ以前に受理した要素は撤回しない。
- 出力に含める並列対象が、すべて正常な非選択で値を持たない場合は、出力もskippedとする。サブworkflowの出力に指定した終点が非選択だった場合などである。
- 失敗を含み成功が0件の場合、continueでは、List出力は空の一覧、Stream出力は空のStreamとし、全体の失敗を維持する。

### 8.4 外側の入力に対する種別

| 外側の入力 | 一回の実行の出力 | 外側の接続の出力 |
| --- | --- | --- |
| なし／Single | List | `Single<List<T>>` |
| なし／Single | Stream | `Stream<T>` |
| Stream | List | 各適用の一覧を流す`Stream<List<T>>` |
| Stream | Stream | 各適用から出る要素を一本に流す`Stream<T>` |

Streamの各要素にconcurrencyを適用する場合、一回の実行の中では、その要素をSingleとして扱う。別の入力に対する結果を、同じ実行の出力へ取り込んではならない。

### 8.5 使い方の例

ユーザーのStreamについて、ユーザーごとに、プロフィールの取得・加工と注文の取得を並行して行い、ユーザーごとにまとめる例である。

```
fetchAllUsers ──Stream──→ concurrency(
                              limit  = 2,
                              tasks  = [profileFlow, fetchOrders],   // profileFlowはB→Cのサブworkflow
                              output = List,
                          ) ──Stream<List<T>>──→ waitStream → 終点
```

ユーザーごとに一回の実行ができ、その中でprofileFlowとfetchOrdersの結果が一つの一覧にまとまる。

## 9. waitStreamとMerge

### 9.1 waitStream

waitStreamは一本のStreamを受け取り、成功結果の一覧をSingleとして返す。

値が利用可能になった時点から取り込み・参照の記録を進める。EOSを待ってから初めて入力を読み始める方式にはしない。

| 入力の終了状況 | 動作 |
| --- | --- |
| 正常終了・結果あり | 成功結果の一覧を返す |
| 正常終了・結果0件 | 空の一覧を返す |
| continueで一部が失敗 | 成功分の一覧を返し、失敗記録を維持する |
| continueで成功分が0件 | 空の一覧を返し、全体の失敗を維持する |
| 経路全体がskipped | waitStreamもskippedとなり、値を出さない |
| 停止・キャンセル | 新しい集約結果を公開せず、停止規則に従う |

順序は保証しない。結果保存はエンジン共通の仕組みを使い、waitStream専用の二重保存を必須にしない。

### 9.2 Merge

Mergeは、同じworkflowの中にある1本以上のSingle接続だけを受け取る。Streamは直接受け付けない。

**各入力接続のtransformは共通の要素型Tを返す。Mergeは得られた成功値を`List<T>`に集め、その一覧を、そのままSingleで出力する。** Merge自身に追加の利用者処理を持たせない。

```
A → transformA → T ─┐
                    ├→ Merge → Single<List<T>> → transform → 後続
B → transformB → T ─┘
```

各入力について値の到着または到着しない理由の確定を待つ。skippedやcontinueの失敗が確定した入力の値を永久に待たない。

成功値だけを一覧へ含める。全入力がskippedならMerge自身もskippedとする。失敗を含み成功値が0件なら、continueでは空の一覧を返し、全体の失敗を保持する。

順序は保証しない。接続元を区別する必要があれば、利用者が各transformの結果にその情報を含める。

waitStreamが返した一覧も、一つのSingle値として扱う。Mergeはそれらを自動で平坦化したり、要素同士をペアにしたりしない。

## 10. 結果、状態、失敗の伝播

### 10.1 値と状態を分離する

結果を持たない理由を、正常なデータに置き換えない。少なくとも次の状態・理由を区別する。内部の型名はこの表記に固定しない。

| 状態・理由 | 意味 |
| --- | --- |
| 待機中／実行可能 | 入力・制御条件・concurrencyの枠などを待っている |
| 実行中 | 利用者処理または制御を進めている |
| 成功 | 正常な処理結果または正常な終了が確定した |
| skipped | branchなどの正常な非選択により実行しない |
| 失敗 | その処理または担当するtransformで失敗が発生した |
| 上流失敗による未実行 | 必要な入力が上流の失敗で得られず、処理を呼ばない |
| 停止による未起動 | 停止が決まり、まだ始めていない処理を起動しない |
| キャンセルによる終了 | キャンセル対象になった処理・Stream生成が終了した。停止決定後に返された値やエラーは新しい成功・業務失敗として採用しない |

非選択や上流失敗により、単発の通常ノードを呼べない場合は、その理由を後続へ伝える。Streamでは、失敗した要素の代わりの値を出さず、残りの成功結果と最終的な終了理由を扱う。

伝播による未実行を、その下流で新たに起こった利用者処理の失敗として重複記録しない。

### 10.2 結果を受理する時点

Singleの戻り値は、その正常完了をエンジンが受理した時点で確定する。Streamの要素は、生成器から取得したその要素を、エンジンが受理した時点で確定する。生成器全体の正常終了を待って、過去の要素を一括して初めて受理する方式にはしない。

失敗・停止・結果受理が競合した場合も、状態遷移としてどちらが先に受理されたかを一意に定める。

受理済みの成功結果は、その後に同じStreamの生成処理または別の処理が失敗しても撤回しない。同じconcurrencyの別の並列対象の失敗も、その理由にならない。

停止・キャンセル決定後の新しい成功結果は受理せず、後続へ渡さない。遅いreturn、取得待ちだった生成器から遅れて返された要素も採用しない。処理や生成器が終了した事実は、終了確認に用いる。

生成器が閉じた後の要素を追加の結果として受理しない。

### 10.3 Streamの終了

入力のEOSだけで、後続の結果Streamを閉じてはならない。

結果StreamのEOSは、新しい入力が来ず、その入力から生じた未完了の処理・Stream生成器・transform・判定がなく、受理済みの転送対象結果を扱い終えた時点で確定する。生成器を表すオブジェクトがreturnされたことを、Streamの正常終了とみなさない。キャンセルを伝えた処理・生成器は、実際に終了するまで未完了とする。

concurrencyは、出力に含めない並列対象についても終了を確認する。サブworkflowは、出力に指定しない終点についても終了を確認する。失敗・非選択の理由も終了時に維持する。

## 11. 失敗方針とキャンセル

### 11.1 指定必須の設定

**停止／continueはノード配置ごとに指定必須とする。** 通常ノードだけでなく、入力transformの受け手となるbranch、concurrency、サブworkflow、waitStream、Mergeの配置も設定を持つ。concurrencyでは、並列対象ごとにも指定する（第8.1節）。

concurrencyのlimitも、正の整数の明示指定を必須とする。通常ノードの同時起動数やStreamの同時処理入力件数は、初版の設定項目に含めない。

### 11.2 continue

失敗を記録し、得られた成功分を流しながら、残りの処理を進める。

失敗した処理の代わりの値を作らない。Stream生成器が失敗した場合も、それ以前の受理済み要素を保持し、残りの独立した処理を進める。生成器の準備・読み進めの失敗には、その生成処理を持つノードの方針を適用する。自動再試行、先頭からの再実行、出力の再送を意味しない。

transformの失敗では、その値による接続先処理の呼び出しを行わない。失敗方針は接続先の設定に従う。

並列対象の失敗を受けたconcurrencyの集計、中の失敗を受けたサブworkflowの呼び出し、Mergeへ届いた「上流失敗で値が来ない」という通知に対し、それを別の新規失敗として停止方針を再適用しない。方針は失敗した処理、または失敗したtransformの接続先で選ぶ。全体の失敗記録は別に維持する。

### 11.3 停止・キャンセル

停止方針の失敗をエンジンが受理したとき、同じ状態遷移でworkflowを停止状態へ移す。

**停止決定後は、新しい処理・transformの呼び出し、Stream生成器の新しい要素取得要求、結果の新規受理、後続への新しい配信を行わない。** 起動済みの処理と生成器にはキャンセルを伝え、終了・クローズの処理を行う。キャンセルと資源の解放に必要な処理は、新しい結果を生成するための呼び出しとは区別する。workflowの最終状態は、キャンセルを伝えた処理と生成器がすべて終了してから確定する。

利用者処理とStream生成器は、キャンセルに応じて終了する契約とする。要素の取得中にキャンセルされた場合も、生成の終了と必要な資源解放を行う。キャンセル前に受理済みの結果は残すが、キャンセル後の遅いreturnや生成要素は採用しない。

停止決定後にキャンセル対象の処理・生成器が返した終了は、値またはエラーの内容にかかわらず、キャンセルによる終了として記録する。停止原因の失敗とは区別し、同じ停止に伴う新しい業務失敗を増やさない。

呼び出し側がworkflow自体をキャンセルした場合も、新規起動と結果受理を止める同じ規則を使う。既に失敗が記録されていれば全体状態は失敗、それがなければキャンセルとする。

停止はworkflow全体に適用する。concurrencyの一つの実行範囲だけを止める設定は、初版に含めない。

### 11.4 全体の失敗

複数の接続の一方の先を含め、一つでも失敗が記録されたworkflowは、最終状態を失敗とする。continueで残りが正常に終わっても、全体を成功へ変更しない。

### 11.5 タイムアウト

利用者の関数を呼ぶ配置には、タイムアウトを任意で指定できる。対象は、通常ノード（Streamを生成するものを含む）、branchの判定、concurrencyの並列対象のうち関数であるものとする。

| 項目 | 規則 |
| --- | --- |
| 計る時間 | 呼び出しの開始から計る。concurrencyの枠を待つ時間は含めない。Streamを受けるノードでは、要素一件ごとの呼び出しに適用する |
| Stream生成 | 生成器の終了までの全体時間とする。次の要素を待つ時間の上限も、別に指定してよい |
| 超えた場合 | その呼び出しの失敗として記録し、原因がタイムアウトであることを区別できるようにする。配置の停止／continue設定を適用する |
| 超えた後 | 呼び出しにキャンセルを伝え、その後のreturnやyieldは受理しない。それまでに受理した要素は残す。呼び出しが実際に終了するまで、concurrencyの枠と完了の判定では実行中として扱う |

Merge・waitStreamには指定しない。待つ時間は、上流のタイムアウトで決まる。concurrencyとサブworkflowの配置全体には、初版では指定しない。一つの実行範囲だけを止める仕組みが必要になるためである。

### 11.6 担当の喪失

利用者の関数の呼び出しは、実行基盤が担当する。担当するのはエンジン自身でも、別プロセスのworkerでもよい。担当する側は、呼び出しを実行している間、担当期限（lease）を延長し続ける。

担当期限が切れた呼び出しは、担当が失われたものとして、その呼び出しの失敗として記録する。原因が担当の喪失であることを区別できるようにし、配置の停止／continue設定を適用する。並列対象では、並列対象の設定を適用する。対象は、タイムアウトと同じく、通常ノード（Streamを生成するものを含む）、branchの判定、concurrencyの並列対象のうち関数であるものとする。

| 項目 | 規則 |
| --- | --- |
| 呼び直し | 担当が失われた呼び出しを、自動で呼び直さない（第16節） |
| 喪失後 | その呼び出しから後で届いたreturn、yield、エラーは受理しない。それまでに受理した要素は残す |
| 終了 | 担当する側がいないため、キャンセルの応答を待たず、その時点で終了したものとする |
| キャンセル中 | 停止やタイムアウトでキャンセルを伝えた後に担当が失われた呼び出しは、キャンセルによる終了として記録し、新たな失敗として記録しない（第11.3節） |
| 期限 | 期限の長さと延長の間隔は、実行基盤が定める |

担当の喪失により、タイムアウトを指定していない呼び出しでも、担当する側が止まったことを検出できる。

## 12. 保存と進行

ノードの成功結果は保存・公開され、後続は利用可能な結果を処理する。保存先はメモリに限定しない。

**遅い後続があるという理由だけで、上流や、複数の接続のほかの行き先を待たせない。** 後続は未処理の結果を自身の進行に従って処理する。Stream生成器に対しても、後続の未処理件数や完了待ちを理由に次の取得を保留するバックプレッシャーを設けない。第4.1.1節の順次取得・受理・保存と、停止・キャンセルの規則に従って読み進める。

未処理件数や保存量が増え得ることは、この方針の実装条件として扱う。ジェネレータを使うことだけでworkflow全体のメモリ使用量・保存量に上限が付くとは保証しない。全件の一覧を生成側で先に作る必要がないことと、結果保存の総量は区別する。waitStream固有の追加保存問題にはしない。

終了・失敗・非選択の通知も、結果を待つ処理が永久に残らないように管理する。受け渡しが済み、終点にも集約にも使わない結果をいつ解放してよいかは、実行基盤が定める。値を保存しただけでは、クラッシュ後に再開できるとは限らない。再開は第12.1節の実行記録による。

### 12.1 実行記録とクラッシュ後の復元

エンジンは、受理した状態遷移を実行記録として順に追記する。一つの状態遷移に伴う記録は、確定の印までを一組とし、確定した組だけを受理済みの状態遷移とする。受理した結果の値は、その状態遷移の確定までに保存する。

実行記録の先頭には、その実行のworkflow構成を記録する。

クラッシュ後は、確定済みの記録を先頭から順に適用して状態を復元し、実行を再開する。確定していない末尾の記録は、途中で途切れていても捨てる。

再開は、記録された構成と、再開する側の構成が同じ内容である場合に限る。異なれば再開しない。利用者処理の実装は構成に含まれないため（第14節）、その同一性は確かめない。

クラッシュ時に実行中だった呼び出しは、担当期限が切れた時点で担当の喪失として扱う（第11.6節）。自動で呼び直さない。

実行記録は、各言語の実装の状態遷移がLeanの定義と一致するかを確かめる検査にも用いる。

## 13. グラフ、終点、戻り値

### 13.1 構造

接続はDAGとし、循環を認めない。

workflowごとに一つのグラフを持つ。接続は、同じworkflowのグラフの中だけに置く。サブworkflowの中のノードへ、呼び出し元のグラフから直接接続してはならない。外との受け渡しは、サブworkflowの入力と、出力に指定した終点だけで行う。

workflow同士の呼び出し関係にも、循環を認めない。workflowが自身を直接または間接にサブworkflowとして呼ぶ構成は、検証で禁止する。

### 13.2 終点

各workflowで、出力先の接続がないノード配置を終点とする。複数終点を認める。

**各workflowの終点は、そのworkflow実行範囲に対してSingleでなければならない。** サブworkflowとして呼ばれるworkflowも同じとする。Streamのまま終点にすることは認めない。StreamはwaitStreamを通してSingleにしてから終える。

サブworkflowの終点は、最も外側のworkflowの結果には含めない。出力に指定した終点の結果だけが、呼び出し元のノードの出力になる。

### 13.3 結果と全体状態

終点の配置名と結果を対応付けて返す。

```
{
    "finish1": finish1の結果,
    "finish2": finish2の結果
}
```

結果を持たない終点に架空の値を作らない。値を持つ終点の結果と、終点ごとの状態・失敗記録・全体状態は区別して取得できるものとする。

型付きAPIでは、各終点とその結果型の対応を保持する。異なる型の終点を、この表記だけを理由にanyへ落とさない。

全体状態は、記録された失敗があれば失敗、失敗なしで呼び出し側のキャンセルがあればキャンセルとする。失敗・キャンセルがなく、全終点が非選択ならskipped。それ以外で全対象が正常に終了した場合は成功とする。

全体完了の判定は、終点の値だけでなく、実行対象の残りの処理、出力に含めない並列対象、サブworkflowの出力に指定しない終点、Streamの終了も確認する。

## 14. 検証と実行API

検証ありのrunと、検証なしのrunUncheckedを提供する。入力の指定方法は両者で共通とする。

| API | 動作 |
| --- | --- |
| run | workflow構成を検証し、失敗した構成は実行しない |
| runUnchecked | 実行前の構成検証を省略し、同じ実行器を使う |

DBから読み込んだ構成にも、必ずロード時に検証することは要求しない。外部更新の可能性を含め、検証を省略する責任は利用者が負う。

runUncheckedでも、結果の受け渡し、transform、停止／continue、キャンセル、タイムアウト、担当の喪失、concurrencyの枠、非選択、終了判断、実行記録は省略しない。

主な構成検証項目は次のとおりとする。

- 配置名・参照先・経路が有効であること。
- 識別子・名前・型名が空でないこと。
- 外部inputの有無・型・入口の契約が整合すること。呼び出し側に内部のSingle／StreamやEOSを指定させる契約を導入しない。
- 処理、transform、接続先の型契約が一致すること。通常ノードについて、一回の呼び出しがSingleを返すかStreamを返すか、およびその要素型が明示されていること。
- 通常ノードの入力接続が1本以下であること。
- 入力を必要としない接続先・並列対象へのtransformがdiscardであり、入力を必要とする接続先・並列対象へのtransformがdiscardでないこと。
- Single／Streamの導出結果と接続契約が一致すること。
- Mergeの入力が1本以上あり、すべてSingleであること。
- 各workflowの終点がSingleであること。
- 各workflowのグラフがDAGであり、workflow同士の呼び出しにも循環がないこと。
- サブworkflowについて、Input型と入力接続、出力に指定した終点と呼び出し元の出力の型が一致すること。
- concurrencyの各並列対象について、入力transform・出力transformの型が一致し、出力に含める並列対象の出力transformがすべて同じ要素型Tを返すこと。
- concurrencyに、出力に含める並列対象が1つ以上あること。
- branchの経路のうち、少なくとも一つが接続先を持つこと。
- 必須の停止／continue設定と、concurrencyの正のlimit（2^64−1以下）があること。
- タイムアウトが、指定できる配置にだけ、正の値（2^64−1以下）で指定されていること。

保存された構成は、ノード定義とtransformの識別子を、実際の処理と型契約へ対応付けて読み込む。保存データ自体に利用者処理の実装を含むことは前提にしない。

型付き構築APIによる型不一致の排除と、構成全体の検証を区別する。未検証データに対し、識別子や宣言だけで型適合が証明されたとみなさない。

不正な構成をrunUncheckedへ渡した場合、正常な構成についての受け渡し・進行・終了の保証は適用されない。必ず成功すること、必ず終了すること、あらゆる不正構成で実装例外が起きないことまでは保証しない。

## 15. Leanの定義と証明

### 15.1 定義するもの

ノードの型契約、配置、接続、並列対象、サブworkflowの呼び出し、実行範囲、Single／Streamの導出、正常性条件、結果保存の抽象モデル、状態と状態遷移を定義する。Stream生成については、生成器の準備、要素の取得、正常終了、失敗、キャンセルによる終了をモデルに含める。タイムアウトは、実行中の呼び出しに起きる外部の事象としてモデルに含め、時刻そのものは扱わない。担当の喪失も、同じく外部の事象としてモデルに含める。実行記録の形式と、確定済みの記録からの復元も定義する。

利用者処理は契約を持つ外部の処理として扱う。内部実装をエンジン側で知ることを前提にしない。受け渡す値は中身を解釈しないデータとして扱い、その内部の状態や使われ方はモデルに含めない（第4.4節）。

保存モデルでは、エンジンが受理したSingleの戻り値と、Stream生成器の各要素を、それぞれ独立した結果として識別する。Stream要素は、少なくとも呼び出しの識別と、その生成器内の出現を区別できるようにする。同じ生成器で値が等しい要素が繰り返された場合も統合しない。この識別は利用者に順序を保証するためではなく、欠落・余計な重複の検証に用いる。保存した結果がどの対象接続へ渡されたかを扱い、順序ではなく受け渡しの対応を証明する。

### 15.2 証明対象

| 対象 | 証明する性質 |
| --- | --- |
| 型付き接続 | 接続元、transform、接続先の型関係を保つ |
| 検証器 | 検証成功した構成が定義した正常性条件を満たす |
| 種別の導出 | Single／Streamと各制御の出力が規則に一致する |
| concurrencyの出力の型 | 出力に含める各並列対象の出力transform後の値が、共通のTを満たす |
| 外部入力の境界 | 外部Input型の値を開始入力として渡し、内部のStream生成・接続規則と混同しない |
| 通常処理 | 必要な各入力にtransformを適用し、出力契約に従って受理した戻り値またはStream要素を対応する後続へ渡す |
| Stream生成 | 生成開始だけで完了とせず、一つの生成器への取得を重複させず、yield要素の受理と終了・失敗・キャンセルを区別する |
| Streamの統合 | 各呼び出しの生成要素を一本へ流し、入力とすべての生成器が終了する前にEOSを確定しない |
| 複数の接続 | 対象となる各接続へ、値の等しさとは別に各結果を正しく渡す |
| branch | 選択結果に従い、非選択側の処理・transformを呼ばない |
| 非選択・失敗 | 正常な空、非選択、上流失敗による未実行を取り違えない |
| サブworkflow | 呼び出しごとに実行範囲を分け、出力に指定した終点の結果と状態だけを呼び出し元へ渡し、中の処理がすべて終わるまで完了としない |
| concurrency | 別実行の状態を混ぜず、登録した並列対象の同時実行数をlimit以下にし、終了した並列対象の枠を解放する |
| waitStream | 対象の成功結果を集約し、処理が残っている間に終了しない |
| Merge | 同じworkflowのSingleの成功結果だけを一覧にし、そのまま出す |
| 受け渡し | 停止しない対象実行では、受理済み結果を各対象接続へ欠落・余計な重複なく渡す |
| 停止 | 停止決定後の新規呼び出し・生成器の新しい要素取得・結果受理・新しい配信を行わず、生成器の終了を処理する |
| タイムアウト | タイムアウトした呼び出しを失敗として扱い、その後のreturnやyieldを受理しない |
| 担当の喪失 | キャンセルを伝える前に担当が失われた呼び出しを失敗として扱い、その後のreturnやyieldを受理しない |
| continue | 失敗した値を流さず、残りを進めながら失敗記録を維持する |
| 全体状態 | 失敗・キャンセル・skipped・成功を規則どおり決める |
| 進行・終了 | 外部前提の下で、正常な構成がエンジンの待機規則や枠管理のために停止し続けず、最終的に終了する |
| 結果の一致 | 停止もキャンセルもされずに終わった実行では、同じ入力と同じ利用者処理の振る舞いから、実行順によらず同じ結果になる（第15.4節） |
| 実行記録と復元 | 記録した状態遷移を検査器で再生すると元の状態になり、確定していない末尾を捨てても確定済みの状態を復元できる。記録の文字列化と読み戻しで内容が変わらない |

停止やキャンセルで配信を打ち切る場合には、その条件を定理に明示する。順序の一致、利用者の副作用のexactly-once、業務処理の意味の正しさを、上記の受け渡し保証と混同しない。

### 15.3 外部前提とエンジンの義務

入力と生成される処理が有限であること、Stream生成器が有限個の要素を生成して終了すること、各要素取得・利用者処理・transform・判定・必要な保存処理が終了すること、キャンセルされた処理と生成器が終了することは、進行・終了の外部前提として明示する。有限でないStreamをwaitStreamで正常に完了できるとは主張しない。

担当期限が切れた呼び出しについて、担当の喪失が実行基盤から通知されることは、進行の外部前提とする。確定済みの実行記録がクラッシュで変わらないことは、復元の外部前提とする。

実行可能な処理を放置しないこと、終了理由を後続へ伝えること、枠を正しく解放することは、エンジン側の義務とする。

同じ生成器へ取得を同時発行しないことは、状態遷移の安全性として扱う。後続の未処理件数を理由に取得を保留しないことは、実行基盤の進行規則としても確認する。単なる非決定的な実行順序の許可だけで、この実装要件まで証明済みとはしない。

待機する制御処理が実行用ワーカーを占有し続け、子処理に必要なワーカーを枯渇させる実装にはしない。concurrencyの論理的なlimitの枠を完了まで保持する規則と、物理ワーカーの占有を区別する。

runUncheckedも、実際に正常な構成を渡した場合は同じ実行器の定理を適用できる。

本書の更新だけでは、Leanの証明も各言語実装への保証も完了しない。実装が仕様を満たすかは別に確認する。

### 15.4 結果の一致

停止もキャンセルもされずに終わった実行について、同じworkflow定義と同じinputで、利用者処理の振る舞いが同じなら、処理をどの順番で進めても、各接続を流れた値の集まり、終点の結果、全体状態は一致する。

利用者処理の振る舞いには、次を含める。

- 呼び出しごとの戻り値と、yieldした各要素
- 失敗、タイムアウト、担当の喪失が起きたかどうかと、Stream生成器では何件目の要素の後に起きたか
- branchの判定結果
- transformの結果と失敗

waitStream、Merge、concurrencyのListが作る一覧は、中身の集まりとして比べる。一覧を受け取る処理は、並び順に依存しないものとする（第5.4節）。

停止やキャンセルで打ち切られた実行は、この性質の対象外とする。打ち切った時点でほかの処理がどこまで進んでいたかは、実行の順番によるためである。

## 16. 初版の対象外

- 通常ノードごとの独自limit・同時起動数設定。
- Streamの同時処理入力件数、およびStream入力のconcurrencyの同時適用数を制限する追加設定。
- 利用者が直接呼ぶemit APIと、その同時・遅延呼び出しを管理する機能。同期・非同期のジェネレータを返し、yieldで要素を生成する機能は対象内とする。
- 専用のexpand制御ノード。一覧の要素をyieldする利用者定義のStream出力ノードで表現できる。
- 分配のための専用ノード。一つの出力から複数の接続を出して表現する。
- concurrencyの内部へのノードの配置。複数ノードからなる処理は、サブworkflowとして定義する。
- concurrencyとサブworkflowの配置全体へのタイムアウト。
- Stream、waitStream、Mergeの一覧の順序保証。
- 複数の接続の先同士の、入力ごとの自動ペアリング。
- 遅い後続の完了や未処理件数を条件に、上流の生成器の取得・結果生成を待機させるバックプレッシャー。
- 自動再試行、先頭からの再実行、出力の再送。
- 循環接続と、workflow同士の循環する呼び出し。
- 呼び出し元の実行から独立したライフサイクルを持つ子workflow。
- concurrencyの一つの実行範囲だけを停止する設定。

サブworkflow、サブworkflowを通したconcurrencyの入れ子、関数またはサブworkflowを並列対象にすることは、初版に含む。

## 設計理由

本章は、仕様本文の規則と、Leanのモデル・各言語の実装で選んだ設計の理由を述べる。動作と契約は本文に、正確な定義と証明済みの主張は[Leanの定義と証明](../Suimon/)による。

### 制御と利用者の処理を分ける理由

利用者の処理内容までモデルに含めると、制御の証明が個々のアプリケーションや実装言語に依存する。そのため、値は識別子だけで扱い、関数・判定・transformの結果は操作の引数として外から与える。これにより、処理本体から独立して、受け渡し・分岐・停止・終了の整合性を検証できる。値の中身や外部への副作用の正しさは、この抽象化の外にある。

### SingleとStreamを宣言せず導出する理由

接続ごとに種別を書かせると、実際の動作と食い違う記述を許してしまう。そのため、種別は関数の出力契約と制御の規則から[導出](../Suimon/Derive.lean)し、書かれた種別と動作を照合する必要そのものをなくす。実行時の件数で種別を切り替えないのは、切り替えると検証時に導出した種別と実行時の形が食い違い、接続の検査を実行前に済ませられなくなるためである。

### 接続ごとにtransformを必須にする理由

接続元の出力と接続先の入力を直接つなぐと、型の食い違いを検証で見つけられない。すべての接続に型付きのtransformを置くことで、型の関係を接続ごとに閉じた形で検査できる。入力を取らない関数を何かの後に動かす場合も、値を捨てる`discard`を通すことで、上流が非選択なら非選択、失敗なら未実行という伝播を例外扱いせずに済む。

### 識別子を来歴から決める理由

同じ値を二度yieldしても二つの結果として扱うため、結果は値ではなく来歴で識別する。来歴だけで決まる識別子は実行順によらず同じになるので、実行順によらない[結果の一致](#154-結果の一致)を識別子のまま比べられる。ランタイムが値に付ける識別子も、中身や到着順ではなく来歴から決める。同じ振る舞いの実行が同じ記録を書き、要素の識別子から作る一覧の識別子も実行順に左右されないようにするためである。

[識別子](../Suimon/State.lean)は、ファイルのパスのように、実行範囲のパスの後にその実行範囲での記録のラベルを置いたものである。ラベルは、呼び出しの契機になった結果など同じ実行範囲のほかの記録を、識別子ではなくラベルで指す。子の実行範囲のパスは、親のパスに持ち主のラベルを一つ足したものである。識別子どうしを埋め込むと、親のパスを含む識別子が子のパスの一段になり、入れ子のたびに長さが倍になる。ラベルだけを積めば、識別子は自分の実行範囲のパスを一度だけ含み、長さは入れ子の深さに比例する。

各部分は[長さ付きで連結](../Suimon/Identity.lean)し、ラベルの先頭に種類のタグを置く。JSON文字列に埋め込む方式では、埋め込むたびにエスケープが倍に増える。長さ付きの連結なら一段あたりの増加は定数で、逆変換があることを証明できる。ハッシュや切り詰めで短くしないのは、異なる記録に同じ識別子が付かないことを、この逆変換による単射性から示せなくなるためである。タグを分けるのは、種類の違う識別子が偶然一致しないことを、単射性だけから示せるようにするためである。

### 実行を操作の列で表す理由

証明用の遷移関係を別に書くと、二つの仕様を保守し、その一致も証明する必要が生じる。そのため、エンジンの判断と外からの報告をすべて[操作](../Suimon/Step.lean)として一つの関数で扱い、探索・実行記録の生成と検査で同じ関数を使う。他言語の実装はこの関数を移したものだけで実行を進め、その記録をこの関数で再生して比べる。スケジューラの選び方は操作の順序として外に出し、証明はどの順序でも成り立つ形で述べる。

### 担当の喪失を失敗として扱う理由

利用者の関数を動かす側が止まったことは、タイムアウトを指定していない呼び出しでは検出できない。そのため担当期限を持たせ、期限切れはその呼び出しの失敗として停止／continueに従わせる。呼び直さないのは、止まったように見える担当者がすでに副作用を起こしたのか、まだ動いているのかをエンジンが知る方法がないためである。呼び直すと、二重実行や受理済みの要素の再送を扱う必要が生じる。

クラッシュ後の再開でも同じ理由で、実行中だった呼び出しは呼び直さず、担当の喪失として扱う。Goのランタイムは利用者の関数を同じプロセスで動かすため、クラッシュした時点で担当者も止まっており、再開時には期限を待たずに喪失を記録する。

### キャンセル後も終了を待つ理由

キャンセルを伝えた時点で終わったものとすると、枠がすぐ空いて次の並列対象が始まり、実際に同時に動く数がlimitを超える。そのため、キャンセルを伝えた呼び出しは実際に終了するまで枠を使い、実行範囲の完了や全体の終了もそれを待つ。キャンセルに応じない処理があると終わらなくなるが、それは[外部前提](#153-外部前提とエンジンの義務)として扱う。待つ時間に上限を設け、過ぎたら担当の喪失とみなす方法は採らない。同じプロセスで動く処理は外から止められないので、全体の終了を報告した後も動き続け、副作用を起こし得るためである。

ただし、担当が失われた呼び出しは応答する側がいないため、キャンセル中でもその時点で終了したものとし、枠を解放する。担当者が実際には動き続けていた場合、同時に動く数が一時的にlimitを超え得るが、応答しない担当者を待ち続けて実行全体が終わらなくなることを避けるため、こちらを選ぶ。

### 実行記録を自前の形式で書く理由

Lean標準のJSONの出力と解析は検証されていないため、記録の文字列化と読み戻しで内容が変わらないことを証明できない。そのため、[記録用の値](../Suimon/Wire.lean)を固定のフィールド順で書き出す[符号化](../Suimon/WireText.lean)を自前で定義し、往復で元に戻ることを証明する。書き出し方が一通りに決まるので、他言語の実装が書いた記録をLeanの出力とバイト単位で比べることもできる。

状態には値の識別子しか現れないため、再開後に後続へ値を渡すにはその中身（ペイロード）が要る。ペイロードを別の保存先に置かず遷移の記録に含めるのは、値の保存と遷移の確定を一度の追記でそろえ、確定した遷移が失われた値を指す状態を復元時に扱わずに済ませるためである。

### 実行記録に構成を含める理由

証明は、一つの構成で動いた実行についての主張である。構成を変えてから途中で再開すると、記録済みの部分と矛盾しない変更（limitを増やす、まだ実行していない配置の設定を変える、など）なら再生が通り、前半と後半で別の構成が動いた実行になる。そのため、実行記録の先頭に構成を書き、再開する側の構成と中身が一致しなければ再開しない。構成を直した後に途中から続けることはできず、最初からやり直すことになる。

記録には、元のファイルのままではなく、構成を決まった形に書き出し直したものを入れる。元のファイルのままでは、空白やキーの順序の違いで同じ構成が別の記録になり、他言語の実装が書いた記録をLeanの出力とバイト単位で比べられなくなるためである。

### 重複したキーを拒否する理由

JSONでは一つのオブジェクトに同じキーを二回書けるが、どちらの値を使うかは規格で決まっておらず、読み込み側によって違う。JavaScriptの`JSON.parse`は後の値を使い、フィールドを先頭から探す読み込みは前の値を使う。そのままでは、同じ実行記録を検査と画面で別の内容として扱い得る。どちらかの値に揃える方法もあるが、重複は書き間違いであることが多く、黙って片方を使うと間違いに気づけないため、構成でも実行記録でもエラーにする。

### 構成の数値に上限を設ける理由

limitとタイムアウトは、各言語の実装で64ビットの整数として扱う。表せない値を黙って丸めると、同じ構成が実装によって別の内容になり、記録の比較や再開時の一致の判定が崩れる。そのため、2^64−1を超える値は読み込みの時点でエラーにする。

### 一覧を中身の集まりとして扱う理由

waitStream・Merge・concurrencyのListの一覧は、順序を保証しない。届いた順に並べると、一覧を受け取る処理の入力が実行ごとに変わり、結果の一致が崩れる。そのため、一覧の値は要素の集まりから決め、一覧を受け取る処理は並び順に依存しないことを利用者の前提とする。

### 結果の一致を実行どうしの包含で示す理由

スケジュールの違う二つの実行を、操作を入れ替えて同じ状態に寄せる証明（合流性）は、concurrencyの枠の取り合いのように、一方を行うと他方が行えなくなる操作の組があるため、そのままでは成り立たない。そのため、完了した実行の状態が、同じ環境に従う別の実行の記録をすべて含むことを一手ずつ示し、両方向の包含から[一致](../Suimon/Theorems/Round3/Determinism.lean)を導く。操作の組ごとの入れ替えを証明せずに済み、補題が操作の種類ごとに分かれるので、並行して証明を進められる。

### 他言語の実装を記録で確かめる理由

各言語の実装とモデルの同値性を形式的に証明するのは、実装言語ごとに大きな作業になる。代わりに、実装が書いた実行記録をLeanの検査器で再生し、状態まで一致することを確かめる。記録が同じ状態遷移で説明できることは確かめられるが、実装全体の正しさの証明ではない。

## 改訂記録

### v1.8

- 実行記録の先頭にworkflow構成を記録し、記録された構成と同じ内容の構成でだけ再開することにした（第12.1節）。
- 並列対象は入力transformの成功後に枠を取得して開始し、入力transformは枠の空きを待たないことを明記した（第8.2節）。
- キャンセルを伝えた後に担当が失われた呼び出しは、キャンセルによる終了として記録し、新たな失敗として記録しないことを明記した（第11.6節）。
- 構成の検証に、識別子・名前・型名が空でないことと、limitとタイムアウトが2^64−1以下であることを加えた（第14節）。
- 別の文書だった設計理由を、本書の末尾の章に移した。

### v1.7

- 利用者の関数の呼び出しを担当する側が止まったことを担当期限（lease）で検出し、その呼び出しの失敗として扱うことにした（第11.6節）。呼び直しはしない。
- 受理した状態遷移を実行記録として追記し、クラッシュ後は確定済みの記録から復元して再開することにした（第12.1節）。第16節の対象外から「保存結果からのクラッシュ再開を保証する機能」を外した。
- 停止もキャンセルもされずに終わった実行では、同じ入力と同じ利用者処理の振る舞いから実行順によらず同じ結果になることを、証明の対象に加えた（第15.4節）。
- concurrencyには、出力に含める並列対象が1つ以上必要とした（第8.1節）。
- Mergeは、1本以上のSingle接続を受け取ることにした（第9.2節）。
- 入力を必要としないノードと並列対象にも、値を渡さないtransform（discard）で入力をつなげることにした（第3.2節、第4.2節、第8.1節）。
- キャンセルを伝えた処理は、実際に終了するまで実行中として扱い、枠と完了・最終状態の判定で終了を待つことにした（第8.2節、第10.3節、第11.3節、第11.5節）。

### v1.6

- 分配のための専用ノード（fanout）を廃止し、一つの出力から複数の接続を出せることにした（第6節）。
- ノードの処理本体として別のworkflowを指定できるサブworkflowを追加した（第4.5節）。呼び出しごとに実行範囲を分け、出力に指定した終点の結果だけを返す。停止・キャンセル・失敗記録は、呼び出し元の実行に従う。
- concurrencyの並列対象を、関数またはサブworkflowに限った。concurrencyの内部にノードを置く構成、前段・後段、非公開の内部枝、公開出力の供給元の指定を廃止した（第8節）。
- concurrencyの出力を、全結果の一覧を返すListと、得られた順に流すStreamの二つにした。出力に含めない並列対象を指定できる。
- 並列対象の枠は、入力transformの成功時に取得し、終了まで保持する形に単純化した。
- 利用者の関数を呼ぶ配置に、タイムアウトを指定できることにした（第11.5節）。
- 制御の役割の一覧を追加した（第1.1節）。
- すべての経路を無処理経路にするbranchを禁止し、保存結果の解放時期は実行基盤が定めることを明記した。

### v1.5

- 受け渡す値についての利用者の保証（第4.4節）を追加した。値が接続先での利用方法と実行基盤の保存・受け渡しの方式に適していることは利用者が保証し、エンジンは値に含まれる反復子やチャネルを複製・復元しない。エンジンは、受理した各結果を各接続へ欠落・余計な重複なく渡すことに責任を持つ。
- Leanのモデルでは、受け渡す値を中身を解釈しないデータとして扱うことを明記した（第15.1節）。
- 並列対象の外から入る接続を、入口ノードへの接続に限った（第8.2節、第13.1節）。
- 入口への入力の種別ごとに、並列対象が枠を取得する時点を定めた。Stream入力の並列対象は最初の要素で枠を取得し、入力StreamのEOSと対象内の処理がすべて終了するまで保持する。要素が一件も届かずに入力が終わった場合は、枠を取得しない。
- 枠を取得した並列対象が、枠を取得していないほかの並列対象を待たないことを明記し、証明対象の「範囲と枠」に加えた。
- 入口への入力を、workflow実行範囲に対するSingleとして導出することを明記した（第3.1節）。
- 検証項目の横断接続の禁止を、入口ノードへの接続に限る規則にまとめた。

### v1.4

- concurrency内部に置けるノード種別を制限しないことを明文化した。型・接続規則、並列対象の途中への横断接続禁止、limitが登録対象だけを数える規則は維持した。
- concurrencyの公開出力定義はちょうど一つとし、公開`Stream<T>`に流す値は各接続のtransform後にTへ統一することを明記した。内部結果の得られ方を理由とした別の「混在許可」は設定しない。
- 公開出力がStreamの場合、内部のSingle結果もyield要素もTとして転送し、公開する辺の種別・要素型を変えないことを明確化した。Singleで公開する既存の経路も維持した。
- runの呼び出し側はworkflowの外部であり、宣言したInput型の値を一つ渡すだけとした。内部のSingle／StreamやEOSを外部inputの指定方式へ持ち込まない。
- Streamの結果はyieldされた要素だけとし、生成終了の戻り値を追加の結果として扱わないことを明記した。
- 生成器の順次取得をエンジンの義務として明記し、呼び出しごとの生成状態を独立させた。利用者処理内部の並行計算は、同じ生成器への同時取得とは区別した。
- 後続の遅さで生成器の読み進めを止めない既定方針を取得規則に反映し、対象外のバックプレッシャーの記述から「必須の」を削除した。
- 新しいemit API、expand制御、入力件数上限、通常ノードのlimitは追加していない。

### v1.3

- 通常ノードの出力契約を、Singleの値またはStreamを返す形に修正した。同期・非同期ジェネレータによるyieldを認め、実行時に件数が決まるStreamを生成できることを明記した。
- emit APIを持たないことと、Streamを返せないことを区別した。専用expandノードの追加は必須とせず、一覧の展開は利用者定義のStream出力処理で表現する。
- 通常ノードのSingle／Stream導出表を更新し、Stream入力・Stream出力では各呼び出しの生成要素を一本に流す規則を明記した。
- 生成器を返しただけで処理を完了扱いしないこと、生成終了まで必要なconcurrencyの枠を保持すること、EOSの確定条件を明記した。
- Streamの途中失敗では受理済み要素を残し、停止・キャンセル後の新しい要素は受理しない規則を明記した。
- 一つの生成器で等しい値を複数回生成した場合も別要素とし、保存モデル・検証項目・証明対象へ反映した。
- 入力件数側の追加上限は今回設けないことを明記した。concurrencyのlimitの意味、通常ノードに独自の上限を設けない方針は維持した。
- 本文から、通常ノードの上限設定の削除経緯を前提とする表現を整理した。以下のv1.2の記録は、その版で行った変更の履歴であり、現行の出力契約は第4節に従う。

### v1.2

- 通常ノード独自のlimit・同時起動数設定を削除した。concurrencyのlimitは、一回の適用内の並列対象数を数える。
- 通常の利用者処理はreturnで結果を返す契約にした。利用者向けemit APIと、一回の通常呼び出しから複数回直接出力する契約を削除した。
- 複数のreturnをエンジンがStreamとして渡すことと、一つの戻り値が一覧であることを区別した。
- 別の並列対象の途中へ接続する構成を禁止した。対象間のMergeは各対象の外で行う。
- concurrencyは公開出力一つ、入れ子可能、非公開の内部終端を許可する仕様にした。
- concurrencyの公開出力の供給元と、Single／Streamの導出を明記した。
- branchはN択と明示的な無処理経路を認め、判定処理の外部アクセスを認めた。
- 上流で失敗して届かなかった値を、branchのskipped判定に加えないことを明記した。
- workflow入力は一つまでで省略可能とした。同じノード定義の複数配置を認めた。
- 停止／continueとconcurrencyのlimitを明示指定必須とした。
- キャンセル後の起動・結果受理・新しい配信を止め、遅いreturnを不採用とした。
- 非選択、上流失敗による未実行、停止による未起動、キャンセル終了を区別した。

### 維持した主要仕様

各接続のtransform、Single専用Mergeと一覧の直接出力、waitStream、終点のStream禁止、分配後のMerge任意、成功分だけを流すcontinue、全体の失敗記録、順序保証なし、run／runUncheckedの選択を維持する。
